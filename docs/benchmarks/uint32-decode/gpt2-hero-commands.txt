Notes
-----
- `numpy` imports 24 spinning OpenBLAS threads by default on this host. The
  tokie and gigatoken children return numpy arrays, so those threads were
  visible in process CPU time and stole cores. All BLAS/OMP pools are pinned
  to 1 in the recorded run; this changes no tokenizer code.
- kitoken's default `encode_specials=False` encodes the literal
  `<|endoftext|>` as 7 regular ids (27, 91, 437, 1659, 5239, 91, 29), not the
  HF special id 50256. The recorded run passes `encode_specials=True` (a
  documented encode argument, not a config edit) so the ids match the HF
  tokenizer.json. With the default, the 459-text validation would fail.
- tiktoken's `encode` raises on the `<|endoftext|>` literal by default; the
  recorded run passes `allowed_special={'<|endoftext|>'}` explicitly. Before
  timing, the tiktoken child also compares all 50,256 non-special ranks and
  the endoftext special against the HF tokenizer.json; the recorded run has 0
  rank and 0 special mismatches (`meta.tiktoken_vocab_check` in the JSON).
- tokenizers 1.0.0rc4 has no `encode` on Tokenizer; the documented path is
  `Tokenizer.from_file(path).compile()` then
  `compiled.encode(text, add_special_tokens=False).ids`. No `encode_fast` or
  ids-only method exists in the installed 1.0.0rc4 stub. HF 0.23.3 keeps
  `Tokenizer.encode(...).ids`.
- The recorded result file contains the full provenance: git HEAD, harness
  sha256, corpus/tokenizer hashes, wheel and native-member hashes, per-round
  order, per-library seconds and CPU time, and the validation checksum.
- No core, binding, README, report, generator, or old raw-data file was
  modified. No commit or push was made.
